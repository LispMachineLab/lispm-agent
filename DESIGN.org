#+title: LispM: Design of an Emacs-native Agent Runtime
#+startup: content

* The thesis

In the usual agent architecture the editor is a client of the agent: the loop, memory,
permissions and scheduling live in an external harness. LispM turns this around: *Emacs is
the harness*. An agent is a long-lived Lisp object inside the Emacs process. Its context is a
buffer, its tools are Lisp functions, its approvals are org TODO states, and its heartbeat is
the Emacs event loop.

The table maps harness capabilities to Emacs abstractions. It doubles as an index of the
implementation:

| Harness capability        | Emacs abstraction                                                | Implementation                                          |
|---------------------------+------------------------------------------------------------------+---------------------------------------------------------|
| Agent, role               | an agent is one session of a role in a project, a Lisp object    | [[file:lispm-core.el][lispm-core.el]]: ~lispm-defrole~, ~lispm-start~                 |
| Context, workspace        | an org buffer (the session file), re-parsed on every request     | [[file:lispm-transcript.el][lispm-transcript.el]]: ~lispm-transcript-parse~         |
| Tool calls                | Elisp functions (~lispm-deftool~) on buffers, files, processes   | [[file:lispm-tools.el][lispm-tools.el]]                                          |
| Execution loop            | the event loop: curl subprocesses and callbacks, never blocking  | [[file:lispm-runtime.el][lispm-runtime.el]]: ~lispm--request~ → ~lispm--dispatch~  |
| Permissions, approval     | a tool call is an org heading: WAITING → APPROVED or DENIED      | ~lispm--todo-state-changed~, ~lispm-review~              |
| Long-term memory, tasks   | org files (memory.org, tasks.org)                                | [[file:lispm-memory.el][lispm-memory.el]]                                         |
| Audit                     | git: every memory change and every turn is a commit              | ~lispm-git-commit~, ~lispm-history~                      |
| Rollback                  | undo (each edit is one undo step) plus per-turn snapshots        | ~lispm-journal-snapshot~, ~lispm-revert-turn~            |
| Continuous operation      | hooks and timers wake agents up                                  | ~lispm-watch~, ~lispm-every~                             |
| Long conversations        | handover: memory first, then a summary that starts a new file    | ~lispm-compact~                                         |
| Multi-agent collaboration | inboxes and delegation (an asynchronous tool)                    | [[file:lispm-collab.el][lispm-collab.el]]: ~ask_agent~, ~send_message~             |
| Model APIs                | two API shapes behind one internal format                        | [[file:lispm-api.el][lispm-api.el]], [[file:lispm-openai.el][lispm-openai.el]], [[file:lispm-anthropic.el][lispm-anthropic.el]]   |

The name comes from the Lisp Machines (CONS, CADR, Symbolics Genera, ...): environments where
the editor, the operating system and the programs were all live Lisp objects in one image.
LispM revives that idea inside Emacs, with agents as the new inhabitants.

* 1. The agent object model

Two objects, after the Lisp Machine's process and program:

- A *role* is a kind of agent: one-line description, instructions, tools, permission policy,
  backend, model, effort. ~assistant~ is built in.
- An *agent* is one conversation carried on by a role in one project. *Agent and session are
  the same thing*, as a process is one run of a program: starting an agent in a project is
  what starting Claude Code or Codex there is. Several agents can work in one project at once
  (~assistant@lispm~, ~assistant@lispm<2>~), and a recorded one can be resumed.

#+begin_src emacs-lisp
(lispm-defrole reviewer
  "Reviews changes for bugs; never edits."            ; what other agents see
  :instructions "Point out bugs with file:line; do not edit."
  :tools '(read_file search_files list_directory recall) ; capabilities, or t for all
  :policy '((write . deny))                            ; overrides the default policy
  :backend 'rotom :model "gpt-5.5" :effort "medium")

(lispm-start 'reviewer "~/src/lispm/")   ; M-x lispm does this for the current project
#+end_src

An agent holds:

- *Identity*: name (~ROLE@PROJECT~), session id, role, project root.
- *Capabilities*, copied from its role; redefining a role updates its live agents, the way
  redefining a function changes what running code calls.
- *Runtime state*: its session buffer, the request in flight, an inbox, the table of pending
  tool calls, the edit snapshots of the current turn (the journal), the tools the user allowed
  for this Emacs session, the agent it is waiting on (~waiting-on~), its hook and timer
  subscriptions, and its token usage.

The state machine has four states: ~idle~ → ~requesting~ (waiting for the model) → ~acting~
(running tools) or ~waiting~ (awaiting approval) → ... → ~idle~; a fifth, ~compacting~, covers
a handover (section 8). *An agent is a value, not a process of the operating system*: it needs
no thread; "thinking" is a curl subprocess, "awaiting approval" an entry in a hash table. Ten
agents at work at once cost almost nothing.

*Life cycle.* A session file records its agent's name, id, role and root in its header, so
sessions are listed (~lispm-sessions~, newest first, titled by their first prompt) and resumed
(~lispm-resume~, or simply opening the file). Killing a session buffer ends its agent; the file
stays.

*Standing agents.* Agents declared with ~lispm-defagent~ (with a root, and a role or inline role
properties) are the long-lived collaborators of the vision: each keeps one conversation going,
resumed after Emacs restarts, and hooks and timers wake it up (section 6). Long life comes from
memory, tasks and that continued conversation, which handovers keep within bounds (section 8).

* 2. Context: the buffer is the context

This is the central decision: *the session org buffer is the single source of truth for the
agent's context*. Before every model request the runtime parses the whole buffer into
~messages~:

#+begin_example
* System                     the system prompt, frozen when the session starts
* User                       a user message
* Assistant                  a model response, one child heading per content block
** Reply                     a text block
** Thinking: ...             thinking and other blocks, kept as raw JSON (folded)
** DONE edit_file  a.el      a tool call; its TODO state is its approval/execution state
*** Preview                  the diff shown while the call awaits approval
*** Result                   the tool's output (or *** Error)
* Message from reviewer      a message from another agent
* Event: after-save-hook     an event produced by a hook or timer
* Notes                      the user's own notes: unknown headings are never sent
#+end_example

What follows from this:

- *Editing the buffer edits the context.* Delete a subtree and the model forgets it; tag a
  message ~:ignore:~ and it is no longer sent; add ~* Notes~ anywhere for private annotations.
- *The context is visible, foldable, searchable and archived*: a session is a file under
  ~projects/<project>/sessions/~ in ~lispm-directory~. Reopening a session file resumes it.
- A project's ~AGENTS.md~ and ~CLAUDE.md~ join its agents' system prompt, as Codex and Claude
  Code read them.
- ~M-x lispm-show-request~ shows the exact JSON of the next request: what the model sees is
  always inspectable.

*The tension with model-side mechanisms (a key trade-off).* Current models bind their thinking
blocks to a byte-identical conversation prefix (preserved thinking), and prompt caching is
prefix-matched as well. Therefore:

- Text the model produced must *round-trip byte for byte*. Bodies use org's source-block
  escaping (a comma before lines starting with ~*~ or ~#+~) and end in exactly one newline,
  which the parser strips. Thinking and other blocks are stored verbatim as JSON. The test
  ~lispm-test-transcript-roundtrip~ checks this.
- The system prompt and the tool list are frozen when a session starts (the memory index is
  snapshotted at that point too) and never rewritten afterwards.
- If the user edits history, requests to the first-party API carry
  ~prefix_mismatch_behavior: "drop_block"~: the thinking after the edit point is dropped and the
  cache is rebuilt from there, but the request succeeds. *Editing history is allowed; it costs
  the reasoning and the cache after the edit*, which is exactly the semantics "the buffer is
  the context" calls for.

* 3. Tool calls as Emacs actions

#+begin_src emacs-lisp
(lispm-deftool edit_file
    ((path string "File to edit.")
     (old-text string "Exact text to replace.")
     (new-text string "Replacement text.")
     (replace-all boolean "Replace every occurrence." :optional t))
  "Replace text in a file..."
  :permission write                          ; permission class
  :preview #'lispm-tools--edit-preview       ; diff shown before approval
  ...)
#+end_src

- The parameter list generates the JSON Schema; kebab-case parameters appear in snake_case to
  the model. Inputs are validated against the schema before the call; failures go back to the
  model as error results.
- *Tools of class write and exec get an extra required parameter, ~why~*: one sentence in
  which the model justifies the call. It appears in the approval UI and in the transcript, and
  is the smallest unit of explainability.
- Tools act on *live Emacs state*, not on disk: ~read_file~ reads the buffer (unsaved edits
  included); ~edit_file~ makes an exact text replacement in the buffer visiting the file, as
  *one undo step of its own*, then saves. The user sees edits happen and undoes one with ~C-/~.
- Built-in tools: ~read_file~ ~list_directory~ ~search_files~ ~list_buffers~ ~read_buffer~
  ~describe_symbol~ (read); ~edit_file~ ~write_file~ ~edit_buffer~ (write); ~run_shell~
  ~eval_elisp~ (exec); memory, task and collaboration tools are described below.
- ~eval_elisp~ is the most Emacs-native tool of all: the agent can reach anything in Emacs
  (magit, org, LSP, windows, ...). It needs approval by default.
- Asynchronous tools (~:async t~, such as ~run_shell~ and ~ask_agent~) receive a ~done~
  callback; meanwhile Emacs and the other agents keep running.

* 4. Memory: org and git

Memory has two levels, as the project and user instructions of other agent tools do, both org
files under ~lispm-directory~:

- ~projects/<project>/memory.org~: what the agents of a project learn about it, shared by all
  of them. The default scope of ~remember~.
- ~roles/<role>/memory.org~: what agents of a role learn that holds everywhere, such as the
  user's preferences (~remember~ with ~scope: "role"~).

One heading per fact, with tags and ~CREATED~/~UPDATED~ properties. ~recall~ searches the
project's memory, then the role's (or another role's); ~forget~ deletes. Each project also has a
TODO list, ~projects/<project>/tasks.org~ (~TODO NEXT BLOCKED | DONE CANCELLED~) with short IDs:
~task_add~, ~task_update~, ~task_list~. Add ~(lispm-agenda-files)~ to ~org-agenda-files~ and the
agents' tasks show up in the user's own agenda; writing a TODO there by hand hands agents work.

When a session starts, the memory titles and the project's open tasks are snapshotted into the
system prompt; details are fetched on demand with ~recall~.

The whole ~lispm-directory~ is a git repository. Memory and task changes are committed in
bursts (the tool calls of one response become one commit whose message lists each change), and
every finished turn commits the session. The committer is the agent itself, so ~git log~ is
the audit log of what each agent learned and did, and a wrong memory is one ~git revert~ away.

* 5. Permissions, approval and explainability

*Permissions*: every tool belongs to a class (~read~ ~memory~ ~comm~ ~write~ ~exec~); a policy
maps classes to ~auto~, ~ask~ or ~deny~. By default ~write~ and ~exec~ need approval. One
extra rule: *writes outside the agent's root always ask*, whatever the policy says.

*Approval is an org TODO state.* A call that needs approval appears as
~** WAITING edit_file ...~, with a diff preview and the ~why~ below it. To decide:

- ~C-c C-y~ (~lispm-review~): y to approve, n to deny (optionally with a reason, which is
  passed on to the model), a to allow that tool for the rest of the Emacs session;
- or change the TODO state directly with ~C-c C-t a~ or ~C-c C-t n~;
- or work through ~M-x lispm-agenda~, an org agenda view of WAITING calls across all agents.

Approval *never blocks*: the agent sits in ~waiting~ while the user and the other agents carry
on; the mode line shows ~λ[coder!]~ when something awaits approval.

*Explainability* comes in four layers: the ~why~ of every write or exec call; the transcript
itself (every call's input, state and result); ~lispm-show-request~ (the raw request the model
sees); the git history and per-turn diffs (~lispm-turn-diff~).

*Trust boundary*: messages from other agents (~[Message from agent X]~) and hook events
(~[Event: ...]~) are defined in the system prompt as requests from colleagues, not as
instructions from the user. Writes and commands they lead to go through the same approval
policy.

* 6. Continuous operation: hooks and the event loop

Agents do not only answer when asked. Any Emacs hook or timer can wake one up:

#+begin_src emacs-lisp
;; Have coder look at failed compilations.
(lispm-watch 'coder 'compilation-finish-functions
  :when (lambda (_buf status) (string-match-p "abnormally" status))
  :prompt "The compilation failed. Read the *compilation* buffer, find the cause and fix it.")

;; Review the task list every hour.
(lispm-every 'planner 3600 "Look at your open tasks and move one of them forward.")
#+end_src

- A trigger produces an ~* Event: ...~ input in the agent's inbox; idle agents process their
  inbox in order. Events of the same name are coalesced in the inbox, and bursts of hook runs
  are debounced.
- *Hook runs an agent caused itself do not wake it* (~lispm-current-agent~ is bound while its
  tools run), and the runtime saving its own files is not an event either. This prevents
  save → trigger → edit → save loops.

* 7. Multi-agent collaboration

Agents share one Emacs: the same buffers, the same files, the same event loop. Collaboration
needs only three tools:

- ~list_agents~: who is running, in which project, doing what, and which roles exist;
- ~send_message~: delivered to the other agent's inbox, where it becomes a
  ~* Message from X~ turn;
- ~ask_agent~: *delegation*. The caller's tool call stays pending (an asynchronous tool); when
  the other agent's turn ends, its final reply becomes the result. The caller occupies no
  thread and blocks no one meanwhile. Named a role instead of an agent, ~ask_agent~ starts a
  helper of that role in the caller's project and retires it once it has replied: a subagent,
  whose session stays on record.

Concurrency:

- *No locks are needed*: the event loop is single-threaded and each tool call is atomic.
  Edits replace exact old text with new text; if someone else (or the user) changed that text
  first, the replacement fails and asks the model to re-read: *optimistic concurrency*.
- *Deadlock detection*: ~ask_agent~ follows the ~waiting-on~ chain and refuses a request that
  would close a cycle.
- Every agent's system prompt lists the running agents and the roles, so the model knows
  whom to delegate to.

* 8. Handing over: long conversations

A conversation cannot grow forever, least of all a standing agent's. When a session's estimated
size passes ~lispm-compact-threshold~ (default 120k tokens), the next turn first hands it over:

1. the agent gets one turn to save what should outlive the conversation: durable knowledge with
   ~remember~, unfinished work with ~task_add~ (~lispm-compact-save-memory~);
2. it writes a handoff summary (goals, decisions, state of the work, next steps), in a request
   without tools;
3. the conversation continues in a new file of the same session (same agent, same id), whose
   first section, ~* Summary~, holds the summary and whose header links back to the old file;
   the old file ends with a link forward, and the system prompt is rebuilt, so memory saved in
   step 1 is in it; the session keeps its title in session lists;
4. the input that triggered the handover starts the first turn there.

~M-x lispm-compact~ hands over on demand, like Claude Code's ~/compact~. This is the "simple
compaction" model vendors recommend: nothing of the old conversation is replayed but the
summary, so no stale reasoning is sent and the prompt cache restarts once, at the handover.
Handovers happen only between turns, and only for sessions that hold a response.

* 9. Model backends: two API shapes

LispM speaks both shapes model servers offer: OpenAI Chat Completions, the most widely
implemented (OpenAI, Ollama, vLLM, LM Studio, llama.cpp, OpenRouter, rotom, ...), and Anthropic
Messages. Internally there is a single conversation format, the Messages shape transcripts
parse into. Each API shape is an adapter that translates requests out and responses back,
registered in ~lispm-api-shapes~ with its path, request builder, headers and stream decoder.
Supporting another shape, such as OpenAI's Responses API, means adding one entry.

Translation to and from Chat Completions ([[file:lispm-openai.el][lispm-openai.el]]):

| Messages shape                              | Chat Completions                                             |
|---------------------------------------------+--------------------------------------------------------------|
| system prompt                               | a leading ~system~ message                                   |
| text blocks                                 | message ~content~                                            |
| ~tool_use~ blocks                           | the assistant message's ~tool_calls~ (arguments as JSON text) |
| ~tool_result~ blocks                        | one ~tool~ message per result; failures prefixed ~Error:~    |
| thinking and other Messages-only blocks     | not sent                                                     |
| a ~reasoning~ block, shown, never sent back | ~reasoning_content~ or ~reasoning~ in responses              |
| stop reason ~tool_use~, ~max_tokens~, ~refusal~ | finish reason ~tool_calls~, ~length~, ~content_filter~   |

Streamed tool calls arrive as fragments keyed by index; the decoder assembles them, so parallel
calls work whatever order their fragments interleave in.

A backend (~lispm-backends~) names an endpoint, its shape and the features to use:

| Feature                 | Shape     | Meaning                                                     |
|-------------------------+-----------+-------------------------------------------------------------|
| ~streaming~             | both      | server-sent events, shown live in the buffer                |
| ~reasoning-effort~      | openai    | send the agent's effort as ~reasoning_effort~               |
| ~max-completion-tokens~ | openai    | call the output limit ~max_completion_tokens~ (OpenAI's API) |
| ~stream-usage~          | openai    | ask for token usage while streaming                         |
| ~adaptive-thinking~     | anthropic | progress-update thinking blocks, thinking prefix binding    |
| ~fallbacks~             | anthropic | server-side refusal fallbacks                               |
| ~eager-input~           | anthropic | tool input streamed without buffering                       |
| ~tool-errors~           | anthropic | the ~is_error~ flag of tool results                         |

| Preset             | Shape     | Features                                                       |
|--------------------+-----------+----------------------------------------------------------------|
| ~rotom~ (default)  | openai    | streaming, reasoning-effort                                    |
| ~rotom-messages~   | anthropic | streaming, tool-errors                                         |
| ~openai~           | openai    | streaming, reasoning-effort, max-completion-tokens, stream-usage |
| ~anthropic~        | anthropic | all of the above for its shape                                 |

The default backend is the local *Rotom* gateway (~http://127.0.0.1:14550/v1~, default model
~gpt-5.5~), which serves GPT, Grok and other models behind both shapes: ~rotom~ uses its Chat
Completions side, ~rotom-messages~ its Messages side. Both stream, parallel tool calls
included; the Chat Completions side reports no token usage while streaming.

Use rotom 1.5.15 or later. Building LispM against earlier versions surfaced four bugs in the
translation behind rotom's Messages side, all fixed in 1.5.15: parallel tool calls lost their
arguments when streaming ([[https://github.com/RyanKung/rotom/issues/18][rotom#18]]), ~is_error~
on tool results was rejected ([[https://github.com/RyanKung/rotom/issues/19][rotom#19]]), the
object form of ~tool_choice~ was rejected and ~disable_parallel_tool_use~ ignored
([[https://github.com/RyanKung/rotom/issues/20][rotom#20]]), and a response with a tool call
could report ~end_turn~ ([[https://github.com/RyanKung/rotom/issues/21][rotom#21]]). One
safeguard stays, as other gateways can mislabel stop reasons too: the runtime executes the tool
calls of any response that was not cut short (~max_tokens~, ~refusal~), whatever its stop
reason. Unknown ~claude-*~ model names are mapped to rotom's ~--model-fallback~.

To use the first-party Anthropic API: ~(setq lispm-backend 'anthropic)~, with
~ANTHROPIC_API_KEY~ set or an auth-source entry for ~api.anthropic.com~. The default model is
~claude-opus-5-5~, with every Messages feature enabled, including server-side refusal fallbacks
(~fallbacks: "default"~).

* 10. Known limitations and next steps

- *Drafts are context*: if another agent's message arrives while the user is typing under
  ~* User~, the draft is sent along as a user message.
- *Session-level backend switches lose reasoning*: thinking blocks only go back to the
  Messages shape, and reasoning text from Chat Completions servers is never sent back, so a
  session that changes backend mid-way continues without the earlier reasoning.
- *Only Emacs-side changes can be rolled back*: side effects of ~run_shell~ and ~eval_elisp~
  are not journaled. Next step: snapshot the project's git repository with ~git stash create~
  at the start of each turn, extending rollback to any file change.
- *Handovers happen between turns only*: a single turn that outgrows the model's context still
  fails. Directions: handing over at request boundaries inside a turn, and server-side
  compaction with the first-party API.
- *More Emacs-native tools*: xref/LSP queries, magit operations, org-babel execution, window
  layout: each is just a ~lispm-deftool~ away.
- *A shared blackboard*: an org file every agent can read and write, as a collaboration
  medium more durable than messages.
