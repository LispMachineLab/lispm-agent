#+title: LispM: Design of an Emacs-native Agent Runtime
#+startup: content

* The thesis

In the usual agent architecture the editor is a client of the agent: the loop, memory,
permissions and scheduling live in an external harness. LispM turns this around: *Emacs is
the harness*. An agent is a long-lived Lisp object inside the Emacs process. Its context is a
buffer, its tools are Lisp functions, its approvals are org TODO states, and its heartbeat is
the Emacs event loop.

The name comes from the Lisp Machines (CONS, CADR, Symbolics Genera, ...): environments where
the editor, the operating system and the programs were all live Lisp objects in one image.
LispM revives that idea inside Emacs, with agents as the new inhabitants.

* 1. The agent object model

Two objects, after the Lisp Machine's process and program:

- A *role* is a kind of agent: one-line description, instructions, tools, permission policy,
  backend, model, effort. ~assistant~ is built in.
- An *agent* is one conversation carried on by a role in one project. *Agent and session are
  the same thing*, as a process is one run of a program: starting an agent in a project is
  what starting Claude Code or Codex there is. Several agents can work in one project at once
  (~assistant@lispm~, ~assistant@lispm<2>~), and a recorded one can be resumed.

#+begin_src emacs-lisp
(lispm-defrole reviewer
  "Reviews changes for bugs; never edits."            ; what other agents see
  :instructions "Point out bugs with file:line; do not edit."
  :tools '(read_file search_files list_directory recall) ; capabilities, or t for all
  :policy '((write . deny))                            ; overrides the default policy
  :backend 'openai :model "gpt-5.5" :effort "medium")

(lispm-start 'reviewer "~/src/lispm/")   ; M-x lispm does this for the current project
#+end_src

An agent holds:

- *Identity*: name (~ROLE@PROJECT~), session id, role, project root.
- *Capabilities*, copied from its role; redefining a role updates its live agents, the way
  redefining a function changes what running code calls. Two things stay as a session started
  with them, since the request prefix is bound to them: its system prompt and the tool list
  offered to the model (section 2).
- *Runtime state*: its session buffer, the request in flight, an inbox (kept in the project's
  ~inbox.org~ too, section 5), the table of pending
  tool calls, the edit snapshots of the current turn (the journal), the tools the user allowed
  for this Emacs session, the agents it is waiting on (~waiting-on~), its hook and timer
  subscriptions, and its token usage.

The state machine has four states: ~idle~ → ~requesting~ (waiting for the model) → ~acting~
(running tools) or ~waiting~ (awaiting approval) → ... → ~idle~; a fifth, ~compacting~, covers
a handover (section 8). *An agent is a value, not a process of the operating system*: it needs
no thread; "thinking" is a curl subprocess, "awaiting approval" an entry in a hash table. Ten
agents at work at once cost almost nothing.

*Life cycle.* A session file records its agent's name, id, role and root in its header, so
sessions are listed (~lispm-sessions~, newest first, titled by their first prompt) and resumed
(~lispm-resume~, or simply opening the file). Killing a session buffer ends its agent; the file
stays.

*Standing agents.* Agents declared with ~lispm-defagent~ (with a root, and a role or inline role
properties) are the long-lived collaborators of the vision: each keeps one conversation going,
resumed after Emacs restarts, and hooks and timers wake it up (section 6). Long life comes from
memory, tasks and that continued conversation, which handovers keep within bounds (section 8).

*Role files.* A role can be an org file too, ~NAME.org~ in ~lispm-role-directories~
([[file:lisp/lispm-roles.el][lispm-roles.el]]): a ~#+description~, ~#+tools~, ~#+policy~ and ~#+effort~ whose values are Lisp
data, and its instructions as the text. It names no backend or model, so that it can be passed
on: its agents use the user's. The files are read when LispM loads (~lispm-load-roles~);
~lispm-install-role~ copies one in once the user has seen it, and ~lispm-delete-role~ deletes
one, its live agents keeping what they copied. Roles defined in Lisp are neither replaced by a
file nor deleted, and a role read from a file and defined again in Lisp is a Lisp role from then
on (~lispm-role-file~).

*Characters* ([[file:lisp/lispm-characters.el][lispm-characters.el]]). An agent is one conversation: when it ends, nobody is
left. A *character* is someone: a name, a soul in the user's words, a picture, and a memory and
a past of its own, which last. A process is one run of a program; a character is rather the
user of a Lisp Machine, who has several activities going at once and is the same in all of
them. It has a conversation going on in each place it is: its own, in no project, which an app of
it shows, and one in each project it is asked into. Each is a standing agent of the character's
role (~lispm-character-agent~): ~ada~ at home, ~ada@lispm~ in a project, its session marked
~#+lispm_character: ada~, so that it resumes as the character's, whatever it was called. All
that drives an agent drives it, sessions, tools, policy, handovers; what it adds is identity:

- *Who it is.* Its system prompt begins with its name and its soul, not ~ROLE@PROJECT~: it is told
  it is one person in many conversations, and where this one is.
- *Its own memory*, ~characters/<name>/memory.org~ (~remember~ with scope ~self~), goes with it to
  every place; a project's memory stays the project's, a role's the role's.
- *Its own past.* Its episodes are kept in its directory, of all its conversations: the
  summaries of its handovers, and a line for each turn of each conversation, its diary, rolled up
  by week and month. A new conversation starts with the latest of them, and with where else it
  has one going: what it did elsewhere, it knows.
- *It grows.* The soul is the user's and stays so; ~revise_self~, a tool only characters have (a
  tool's ~:for~), writes ~self.org~, what it came to know of itself, which its conversations start
  with too. Each revision is a commit, and it tells the user.
- *Its own model.* ~#+backend~ names one of ~lispm-backends~, or ~#+endpoint~ is an endpoint of its
  own, as an entry of ~lispm-backends~ is, by the name ~@ada~ (~lispm-backend~); without them, it
  thinks with the user's. Its file is under git, so it holds no key: an endpoint says where its
  key is, with ~:key-env~ or ~:key auth-source~.

A character is its directory, ~characters/<name>/~ in ~lispm-directory~: ~character.org~, written as
a role file is (keywords, then the soul), its picture, ~self.org~, ~memory.org~, ~episodes/~, and
the ~tasks.org~ of its own conversation. ~lispm-character-form~ makes or changes one, the form
~lispm-new-character~ and ~lispm-edit-character~ show; ~lispm-save-character~ does it from Lisp,
and its file, edited by hand, is read again when saved. ~lispm-character-change-functions~ tells a
desktop when to show an app of it, which the agent knows nothing of.

*Forms* ([[file:lisp/lispm-form.el][lispm-form.el]]). A form is data: a title and fields, each a key and a plist
saying its type (~text~, ~text-area~, ~picture~, ~choice~, ~radio~, ~check~, ~heading~), its label,
whether it is required, how it is checked, and when it is shown, as a function of the values.
~lispm-form~ draws it with Emacs's widgets (wid-edit.el), which edit, move from field to field
and press buttons as Customize does, in a graphical frame or a text terminal alike; it is drawn
again when a choice shows or hides fields, keeping what was typed. It is laid out as a dialog:
the labels flush right in a column, each control beside its label and its help under it, the
fields one width (~lispm-form-width~), a text area a framed panel as wide, the fields after a
heading in a group box, the buttons at the bottom right. Positions are pixels measured in the
buffer's own faces, remapped or not, so a field is as wide in a proportional face as in Emacs's
own: a text field's padding is drawn as one blank reaching the fields' right edge.

A form knows nothing of where it is shown: whatever shows it dresses it, as a desktop does in its
look. ~lispm-form-glyph-function~ gives the pictures of its buttons, check boxes, radio buttons,
pop-up menus and pictures; ~lispm-form-group-function~ the edges of its group boxes;
~lispm-form-choose-function~ shows a pop-up menu's choices. Its faces may be remapped, before it is
drawn (~lispm-form-mode-hook~), so that it is measured in them, and ~lispm-form-show-header~ set to
nil where its window is titled with it. ~lispm-form-drawn-hook~ runs whenever it is drawn, as
~lispm-form-redraw~ draws it again. Being data, a form is one an agent could fill in as well as a
person.

*A character's chat says who it is*: its picture, its name, what it is told to be, where the
conversation is and what it thinks with, in place of LispM's welcome; its replies start with its
picture. ~lispm-character-conversations~ and ~lispm-character-days~ tell where a character has
conversations and what it did lately, for whatever shows it.

*An app is a character too*, of a kind: its soul is its skill (section 11), whose code its
conversations evaluate from the start, so its tools are theirs; its picture is its icon; it
thinks with a model the user chose, or LispM's. The program bringing it makes it one each time
it loads (~lispm-define-app-character~); what the user chose for it goes into a character file of
its name without a ~#+title~, which comes first and makes no character while the app is gone. An
app has one conversation, its own, wherever it is asked from. Others meet it in two ways, as an
object and as a subject: with its skill and its tools, which they use themselves when they know
what to do, at the cost of one request; or asking it, which costs a conversation of its own but
brings its judgment, what it remembers of the user, and keeps many steps out of the asker's
context. The second is always built on the first, and the user's =@Name= always asks for it.
Apps are named apart from other characters in system prompts, so that they do not crowd them.

* 2. Context: the buffer is the context

This is the central decision: *the session org buffer is the single source of truth for the
agent's context*. Before every model request the runtime parses the whole buffer into
~messages~:

#+begin_example
* System                     the system prompt, frozen when the session starts
* User                       a user message
* Assistant                  a model response, one child heading per content block
** Reply                     a text block
** Thinking: ...             thinking and other blocks, kept as raw JSON (folded)
** DONE edit_file  a.el      a tool call; its TODO state is its approval/execution state
*** Asks: write_file  b.el   a call a Lisp program in this one makes, awaiting approval
*** Preview                  the diff shown while the call awaits approval
*** Result                   the tool's output (or *** Error)
*** Stopped                  an error the call stopped at, awaiting a restart (section 5)
* Message from reviewer      a message from another agent
* Event: after-save-hook     an event produced by a hook or timer
* From LispM                 LispM passing on a choice of the user's (section 5)
* WAITING Condition: ...     the turn stopped early, awaiting a restart (section 5)
* Notes                      the user's own notes: unknown headings are never sent
#+end_example

What follows from this:

- *Editing the buffer edits the context.* Delete a subtree and the model forgets it; tag a
  message ~:ignore:~ and it is no longer sent; add ~* Notes~ anywhere for private annotations.
- *The context is visible, foldable, searchable and archived*: a session is a file under
  ~projects/<project>/sessions/~ in ~lispm-directory~. Reopening a session file resumes it.
  A linked git worktree is the project of its main worktree (~lispm--main-worktree~ reads
  the ~.git~ file and ~commondir~ git leaves there, without running git), so its agents share
  the main one's sessions, memory and tasks.
- A project's ~AGENTS.md~ and ~CLAUDE.md~ join its agents' system prompt, as Codex and Claude
  Code read them.
- ~M-x lispm-show-request~ shows the exact JSON of the next request: what the model sees is
  always inspectable.

*The tension with model-side mechanisms (a key trade-off).* Current models bind their thinking
blocks to a byte-identical conversation prefix (preserved thinking), and prompt caching is
prefix-matched as well. Therefore:

- Text the model produced must *round-trip byte for byte*. Bodies use org's source-block
  escaping (a comma before lines starting with ~*~ or ~#+~) and end in exactly one newline,
  which the parser strips. Thinking and other blocks are stored verbatim as JSON. The test
  ~lispm-test-transcript-roundtrip~ checks this.
- The system prompt is frozen when a session starts (the memory index is snapshotted at that
  point too) and never rewritten afterwards. So is the tool list, as long as the session is
  open (~lispm-session-tools~): tools defined later, or a role redefined with other tools,
  reach the next session or the next handover. The exception is an agent whose tools grow on
  purpose mid-session (~lispm-tools-changed-functions~), as when it finds deferred tools,
  loads a skill or defines a tool itself (section 10): the new tools are added after the
  others, and the prefix changes once. A tool defined again runs its new body at once, but
  keeps in a session the schema the session first offered.
- If the user edits history, requests to the first-party API carry
  ~prefix_mismatch_behavior: "drop_block"~: the thinking after the edit point is dropped and the
  cache is rebuilt from there, but the request succeeds. *Editing history is allowed; it costs
  the reasoning and the cache after the edit*, which is exactly the semantics "the buffer is
  the context" calls for.

*Storage is not the interface.* The org buffer is the right store (exact, editable,
diffable, archived) but a poor place to hold a conversation: you would type into the record
itself, and approving a call would mean editing a heading. So people talk to an agent in a
chat ([[file:lisp/lispm-chat.el][lispm-chat.el]]) laid out like Claude Code's terminal interface, and the org buffer stays
out of sight under a hidden buffer name. The chat owns nothing: it is a view, redrawn from the
org buffer (throttled, from the first item that changed) whenever that buffer or the agent's
state changes. Your message goes through ~lispm-tell~ like any other input; the chat's input
area is not part of the context, so a draft is never sent by accident. Tool calls are shown by
kind (~Read(path)~ with a line count, ~Update(path)~ with its diff, ~Bash(command)~ with its
first lines of output), and ~TAB~ shows any of them in full. ~/transcript~ opens the org
document for the edits above; ~lispm-interface~ set to ~org~ makes it the interface again.

*A terminal, as the Lisp Machine had* ([[file:lisp/lispm-terminal.el][lispm-terminal.el]]). A Lisp Machine's console was a
listener and a who line, the system reached by typing at it. LispM's terminal is the same: a
frame with no bars, the sessions on the left, the listener on the right, which is the chat of
one session, and a who line along the bottom. It adds no state of its own: the sessions are
~lispm-agents~ and ~lispm-sessions~, the listener is ~lispm-chat~, and it is drawn again from
the hooks the chat already listens to. LispM itself, the system's own agent, comes first, so
that with no project at hand there is still someone to ask.

*Objects, not strings* ([[file:lisp/lispm-inspect.el][lispm-inspect.el]]). On a Lisp Machine the screen showed objects: Genera's
presentations made a pathname or an instance on the screen the object itself, with commands by
its type. The chat does the same. A presentation is text whose ~lispm-object~ property is the
object it shows: a file and a line, a buffer, an agent, a symbol, a tool, a call. The chat
presents a call's argument (~Read(a.el)~ is the file), the ~file:line~ places and org links in
replies and results, agents' names, and code that names a symbol or a file; ~RET~ or a click
acts by type: the file is visited at the line, the agent inspected, the symbol described, the
tool's definition shown, the call found in the transcript. They look as they would and light up
under the mouse, as Genera's did. The *inspector* (~lispm-inspect~) shows one agent whole, as
Genera's inspector showed an object: identity, state and model, policy and ceiling, the calls it
has pending and what they ask for, its inbox, whom it waits on and who waits on it, the files
its turns changed, its tools and triggers, all of them presentations; agents have it as the tool
~inspect_agent~.

*Grounding* ([[file:lisp/lispm-ground.el][lispm-ground.el]]). A model writes a name with the same confidence whether or not
anything has it, and asking the model again asks the source of the mistake; the image it talks
to knows. As SWI-Prolog's PceEmacs colours a call to an undefined predicate by asking the
loaded program, the chat checks the code in a reply against the running Emacs: a symbol no
loaded code mentions, in the namespace of a loaded library (~lispm-~, ~org-~, ~cl-~ of cl-lib); a
call of a function nothing defines, or giving it more or fewer arguments than ~func-arity~
allows; a path to a file that is not there. Such code is underlined in ~lispm-ungrounded~ and
says why under the mouse or with ~C-h .~; names the reply defines in a code block (and their
-hook, their accessors), words Emacs knows (a text property), libraries on ~load-path~ and the
dashed words of other languages (~text-align~) pass. Reading a reply's forms uses an obarray of
its own, so made-up names stay unknown to the image. What is found is data, ~(undefined NAME)~,
~(arity SYMBOL GIVEN ARITY)~ or ~(missing FILE)~, ready to be told to the model as well.
~lispm-ground-code~ turns it off, and the open chats are drawn again without it.

* 3. Tool calls as Emacs actions

#+begin_src emacs-lisp
(lispm-deftool edit_file
    ((path string "File to edit.")
     (old-text string "Exact text to replace.")
     (new-text string "Replacement text.")
     (replace-all boolean "Replace every occurrence." :optional t))
  "Replace text in a file..."
  :permission write                          ; permission class
  :diff #'lispm-tools--edit-diff             ; text before and after, diffed for approval
  ...)
#+end_src

- The parameter list generates the JSON Schema; kebab-case parameters appear in snake_case to
  the model. Inputs are validated against the schema before the call; failures go back to the
  model as error results.
- *Tools of class write, shell and exec get an extra required parameter, ~why~*: one sentence in
  which the model justifies the call. It appears in the approval UI and in the transcript, and
  is the smallest unit of explainability.
- Tools act on *live Emacs state*, not on disk: ~read_file~ reads the buffer (unsaved edits
  included); ~edit_file~ makes an exact text replacement in the buffer visiting the file, as
  *one undo step of its own*, then saves. The user sees edits happen and undoes one with ~C-/~.
- Other programs change files too: a shell command, git, the user's own shell. A buffer whose
  file changed on disk is brought up to date before a tool uses it, and never by asking, as
  Emacs would (~lispm-tools--state~): without unsaved changes it is reverted; with them it is
  in conflict with its file, which a change reports to the model as an error (~read_file~
  shows the buffer and says so; ~lispm-revert-turn~ reverts nothing until the user settles
  it). A session transcript is never reverted, since the runtime holds positions in it; a
  buffer whose file was deleted becomes the buffer of a new file when a tool writes it; a file
  too large to visit without Emacs asking is refused. So is a directory, and a file that is
  not writable, before it is visited or journaled: Emacs would visit it read-only, and a
  buffer the user made writable (~C-x C-q~) would still ask before it is saved, so a tool
  changes that buffer only while ~lispm-save-edits~ is off, which leaves saving to the user;
  a read-only buffer is not changed at all. After a call that may have changed
  files (not one of class ~read~, ~memory~, ~comm~ or ~web~), the unmodified buffers of the
  files under the agent's root that changed on disk are reverted, so the user sees what a
  command, Lisp or an MCP server did there (~lispm-revert-after-calls~); proposals laid over
  a reverted buffer are made again. Previews and the changes shown while a call is written
  change nothing: like ~search_files~, the turn diff and the system prompt's instruction
  files, they read an out-of-date buffer's file from disk (~lispm--file-text~).
- ~search_files~ is Emacs-native as well, with no grep or ripgrep behind it: project.el
  (~project-files~) lists the files, so a git project's ~.gitignore~ applies, and Emacs
  regexps search them, in the file's own buffer when Emacs visits it, so unsaved edits are
  found as ~read_file~ shows them. It works in slices of 30 ms between which Emacs handles
  input, so a long search never freezes it. Models write regexps in ripgrep's syntax
  (~(a|b)~, ~\d~, ~x{2}~); ~lispm-tools--emacs-regexp~ translates them, and refuses what
  Emacs regexps lack (lookaround) rather than silently matching something else.
- Built-in tools, the core layer every agent carries (section 10 explains the deferred others
  and ~search_tools~): ~read_file~ ~list_directory~ ~search_files~ ~list_buffers~ ~read_buffer~
  ~describe_symbol~ ~apropos~ ~search_tools~ ~skill~ (read); ~edit_file~ ~write_file~
  ~edit_buffer~ (write); ~run_shell~ (shell); ~eval_elisp~ (exec); ~run_lisp~ (lisp); the
  memory, task and collaboration tools described below. Deferred, as seldom needed:
  ~read_info~ (read), ~write_skill~ (exec), ~forget~ (memory), ~list_agents~ ~inspect_agent~
  ~start_agent~ (comm); and for Lisp in the image (below): ~xref_definitions~ ~xref_references~
  ~flymake_diagnostics~ (read); ~edit_definition~ (write); ~eval_definition~ ~ert_run~ (exec).
- *Emacs is the operating system*, so LispM does not wrap its functions in tools one by one:
  ~eval_elisp~ reaches anything in Emacs (magit, org, LSP, windows, the network, ...), and
  what an agent lacks is knowing what there is. It finds out as a person would: ~apropos~
  finds the functions, commands and variables named after something, ~describe_symbol~
  documents one, ~read_info~ reads the manuals of Emacs and its packages, by node or through
  their indexes. Asynchronous work (a process, a page loading) ends with
  ~(lispm-async (lambda (resolve) ...))~, and eval_elisp waits for the value. A tool the
  code defines with ~lispm-deftool~ is the agent's from its next step on (section 10), until
  Emacs exits, unless the agent keeps it in a skill (section 11). eval_elisp
  needs approval by default. An error in the evaluated code comes back with its backtrace,
  innermost call first: the frames of that code alone, from where the error was signaled
  (caught with ~handler-bind~, before the stack unwinds) up to the ~eval~ of the form, at
  most 20 of them; so the model sees which function called which with what, as a person
  would in the debugger. The handler runs for errors the code catches as well, so it only
  collects the frames; they are printed once an error reaches eval_elisp. They show the
  arguments of those calls, values the model may not have seen otherwise (a password read with
  ~auth-source~): ~lispm-eval-backtrace~ turns them off.
- *Lisp under policy* (lispm-lisp.el). Between a tool call and ~eval_elisp~ there is
  ~run_lisp~: a program in which the agent's tools are functions,
  ~(edit_file :path f :old-text a :new-text b)~, so that reading ten files, filtering them and
  editing three is one step rather than a dozen, as on a Lisp Machine the user's language and
  the system's were one. Each call goes through the agent's policy as the model's own would:
  reads run, a write awaits approval, asked in the chat as any is and recorded under the
  program's call (a ~*** Asks:~ subsection, with its preview), and a denial signals
  ~lispm-call-denied~, which the program may handle. Otherwise a program only computes. It is
  checked before it runs, against an allowlist: the special forms, common macros (~let~
  ~dolist~ ~pcase~ ~cl-loop~ ~when-let*~ ~with-temp-buffer~ ...), the functions Emacs declares
  free of side effects (the ~side-effect-free~ and ~pure~ declarations the byte compiler
  relies on) and a few more of the kind; it binds no variable of Emacs's but a handful such as
  ~case-fold-search~, and sets only its own. What can be checked only as it runs is checked
  then: a function it hands to ~mapcar~ or ~funcall~ must be a lambda of its own or an
  allowed function; it changes only buffers and hash tables it made, moves point in others
  only inside ~save-excursion~, throws only to its own catches, and cannot handle ~quit~, so
  C-g stops it; destructive list functions (~nreverse~ ~nconc~ ~sort~) work on a copy. File
  name handlers are off while it runs, so no TRAMP connection opens, and the text it gives
  tools or returns loses its properties, which could hold code run on display. A macro that
  expands its body while it is expanded (~cl-flet~, ~rx~) has the body searched first for
  macros a program may not use: ~eval-when-compile~ would run there unchecked.

  An Emacs Lisp evaluation cannot pause to wait for an approval or an asynchronous tool, so a
  program is run again instead. The call that must wait ends the run; once its result is
  in, the program runs from the start, and the calls it made before get the results recorded
  for them, without running again. Its computations being free of side effects, a run
  replays the one before; if what it reads has changed and it makes other calls, those are
  new calls, under the policy like the first. Its result lists the calls it made (those
  denied or failed marked), then what it printed and its value.
- *Lisp in the image* (lispm-develop.el). On a Lisp Machine a program grew in the world it
  ran in: one definition edited, evaluated into the image, tried, with an editor that knew
  where each definition was and who used it. Agents work so on Emacs Lisp with deferred tools
  (section 10, the source ~lisp~). ~edit_definition~ replaces the form that defines a
  function, macro, variable or face, found as ~find-function~ finds it: its file from
  ~find-function-library~ or ~symbol-file~, or a file given, for a definition not evaluated
  yet; the form in it by the searches of ~find-function-regexp-alist~. The model writes the
  new form only, which must read as one form defining that symbol, and the edit is made as
  ~edit_file~'s are: one undo step, journaled, saved, previewed as a diff and shown in place.
  The search is made in the text the tool goes by, never through ~find-file-noselect~, which
  would ask about a buffer out of date, and never as find-function's last resort, by
  expanding every macro of the file, which would run its code. ~eval_definition~ (~exec~)
  evaluates the definition from its file's buffer as C-M-x does, by ~eval-defun~'s own means:
  with the file's ~lexical-binding~, a ~defvar~, ~defcustom~ or ~defface~ reset to what it
  now says, and the file recorded as where the definition comes from; but its value is the
  result, not a message. ~ert_run~ (~exec~) runs ERT tests in the image, loading a file of
  them first if asked, and returns a summary, then each failure with its condition and the
  innermost calls of its backtrace, up to the test's body; a test C-g quits stops the run.

  Two tools serve code in any language: ~xref_definitions~ and ~xref_references~ ask the
  xref backend of the code's buffer, Emacs Lisp's own by default, a language server's with
  eglot, which answers about a position, so point is put on the identifier first (on the
  line given); ~flymake_diagnostics~ runs a buffer's flymake backends and waits for their
  reports without blocking (~:async~), the byte compiler and checkdoc for Emacs Lisp.
  Flymake is turned off again where it was off, and a file visited only to be read is closed
  again. The byte compiler runs the code it compiles, so Emacs lets it check only a file the
  user trusts (~trusted-content~); LispM never trusts one on its own, and when the compiler
  did not run, the result says so rather than reporting no warnings.
- Asynchronous tools (~:async t~, such as ~run_shell~ and ~ask_agent~) receive a ~done~
  callback; meanwhile Emacs and the other agents keep running.
- *C-g interrupts a call* while Emacs runs it. Calls run from the process sentinels and timers
  of the loop, where Emacs inhibits quitting; ~lispm-tool-invoke~ allows it again while a tool
  runs, so a runaway computation, a loop in ~eval_elisp~ say, can be stopped. The interrupted
  call fails, and the turn goes on; ~run_shell~ interrupted while it starts its command stops
  the command too. What a call waits for afterwards (a process, a promise, another agent) is
  stopped by aborting the turn. Only the tool is interruptible: what follows it, its result and
  the rest of the turn, is not, so C-g never leaves the runtime half way or reports a call that
  ran to its end as interrupted, and a C-g pressed before the call began is left for whatever
  it was meant for.

* 4. Memory: org and git

Memory has two levels, as the project and user instructions of other agent tools do, both org
files under ~lispm-directory~:

- ~projects/<project>/memory.org~: what the agents of a project learn about it, shared by all
  of them. The default scope of ~remember~.
- ~roles/<role>/memory.org~: what agents of a role learn that holds everywhere, such as the
  user's preferences (~remember~ with ~scope: "role"~).

An agent of the whole system (~lispm-defagent~ with ~:system t~), such as the agent of a
system-wide prompt, works in no project: its own memory, tasks and episodes are the system's,
~system/memory.org~ and so on, in place of a project's. Agents of projects do not see them.

A character (section 1) has a third: ~characters/<name>/memory.org~, its own, which it reads first
in every conversation it has (~remember~ with ~scope: "self"~); its own conversation, in no
project, has it in place of a project's, as a system agent has the system's.

One heading per fact, with tags and ~CREATED~/~UPDATED~ properties, and ~RECALLED~/~RECALLS~: when
~recall~ last returned it, and how often. ~recall~ searches the agent's own memory, then the
role's (or another role's); ~forget~ deletes. Each project, and the system, also has a TODO list,
~tasks.org~ (~TODO NEXT BLOCKED | DONE CANCELLED~) with short IDs: ~task_add~, ~task_update~,
~task_list~. Add ~(lispm-agenda-files)~ to ~org-agenda-files~ and the agents' tasks show up in the
user's own agenda; writing a TODO there by hand hands agents work.

When a session starts, the memory titles and the open tasks are snapshotted into the system
prompt; details are fetched on demand with ~recall~. The prompt lists at most
~lispm-memory-max-entries~ titles (default 200) of the agent's own and its role's memory together,
those used most lately, each memory followed by a line saying how many more it has: nothing is
left out unseen.

*Consolidation.* Memory that only grows would outgrow any prompt, so it compresses itself. Once a
turn has ended, a memory past its budget, ~lispm-memory-max-entries~ entries or
~lispm-memory-max-tokens~ tokens (default 30k), is consolidated when Emacs is idle
(~lispm-idle-delay~, 5 seconds). A model, ~lispm-memory-model~ if set (a small one does), gets
every entry with its history and returns a plan to bring the memory to three quarters of its
budget: entries that say the same thing merged, old entries seldom recalled folded into summary
entries by topic, stale ones dropped with a reason. The plan is checked (every entry it names
exists and is named once, a drop has a reason) and carried out only if the memory did not
change meanwhile; entries it does not name stay as they were. A merged entry keeps the earliest
~CREATED~, the latest ~RECALLED~, the sum of ~RECALLS~, and names its sources in ~MERGED~. The
change is one commit by the agent, whose message names every entry merged or dropped and why,
so ~git revert~ undoes it; without git (~lispm-git~ nil) memory is never consolidated. A plan
must bring the memory nearer its budget and leave no two entries of one title. Each pass costs
a request holding the whole memory, so a memory is not tried again before it says something new
(when entries were recalled does not count), nor for six hours after a pass that failed or
freed nothing.

*Episodes.* Memory holds what is known; episodes, what happened. The summary of every handover
(section 8) is kept in ~episodes/YYYY-MM-DD.org~ beside the agent's own memory. Once a week is
over its days are rolled up, by a model at idle, into ~episodes/YYYY-Www.org~, and once a month is
over its weeks into ~episodes/YYYY-MM.org~ (a week belongs to the month of its Thursday); the
files rolled up are removed in the same commit, so rollups too wait for git, and a rollup
removes nothing that changed after it was asked for. A new session of an agent of the whole system
starts with the latest episode in its system prompt (~lispm-episodes~).

The whole ~lispm-directory~ is a git repository. Memory and task changes are committed in
bursts (the tool calls of one response become one commit whose message lists each change), and
every finished turn commits the session. The committer is the agent itself, so ~git log~ is
the audit log of what each agent learned and did, and a wrong memory is one ~git revert~ away.

* 5. Permissions, approval, restarts and explainability

*Permissions*: every tool belongs to a class (~read~ ~memory~ ~comm~ ~lisp~ ~write~ ~shell~
~exec~); a policy maps classes to ~auto~, ~ask~ or ~deny~. By default ~write~, ~shell~ and ~exec~
need approval. ~lisp~, the class of ~run_lisp~, implies ~read~: a program reads Emacs as it
computes, so an agent that may not read may not run one either. One extra rule: *writes
outside the agent's root always ask*, whatever the policy says, whether a ~path~ argument names
the file, a ~buffer~ argument a buffer visiting it, or the tool says which files a call changes
(~:targets~ in ~lispm-deftool~): ~edit_definition~ finds its file from a symbol, which may be
anywhere, Emacs's own sources included. A write whose files cannot be told asks too. So does
every call of a tool declared ~:always-ask~, such as ~write_skill~ (section 11), whose effect
outlasts the session: what it saves is code that later sessions evaluate, which no policy should
let an agent decide alone. A policy that denies the tool's class still denies it.

*Checks from outside* (~lispm-tool-action-functions~). What else should hold a call back LispM
cannot know: which MCP servers the user trusted, what a session has read. So another program,
a security application, may look at every call LispM's own rules do not deny, with the agent,
the tool and the input, and answer nothing, ~ask~ or ~deny~, with a reason (~lispm-tool-decision~).
The strictest answer wins: a check can tighten what LispM decided, never relax it. A check that
fails, or answers anything else, asks: one that fails open is no check, and an error must never
let a call through. The reason goes where the user decides, in the call's ~*** Preview~ (so a
reopened session still has it) and the chat's approval box, and a denial tells the model why.
Allowing a tool for good does not silence a check: what the user allowed is asked again while a
check asks, and approving one call for good approves no other waiting call a check still asks
about. MCP servers' tools have a check of their own when they are registered (section 10).

*Unrestricted code is outside the permission model.* ~eval_elisp~ (~exec~) reaches all of
Emacs, and ~run_shell~ (~shell~) all of the system, Emacs included, while the agent's root is on
this machine: what they run can change the policy of the agent running it, lift a helper's
ceiling, or call a tool's function past its checks. The policy cannot mediate what such a call
does, only whether it runs: it runs if the user approves it, or if the policy lets its class
run unasked, which gives the agent everything. So approving one "for good" (~2~ in the chat,
~a~ in the review) allows that exact call again, with the same input, never every later one
(~lispm-tools-allowance~), and so does approving a call of a tool that always asks. Lisp the
policy should mediate is what ~run_lisp~ is for.

*Commands and Lisp are apart.* Shell commands were of class ~exec~, as Lisp is; they have a
class of their own, ~shell~, so that a policy can let commands run unasked while Lisp asks,
which is what an agent whose root is on another machine wants (below). A policy that does not
name ~shell~ gives it what it gives ~exec~ (~lispm--permission-fallbacks~), so policies,
customized defaults and helpers' ceilings recorded before the split mean what they meant.

*A sandbox for commands* ([[file:lisp/lispm-sandbox.el][lispm-sandbox.el]]). The policy decides
whether a command runs, never what it does once it runs; a sandbox decides that, and it has to
be the operating system's, since a command is a process Emacs cannot watch. LispM uses
Anthropic's sandbox runtime, srt: ~sandbox-exec~ on macOS, bubblewrap on Linux, and a proxy that
checks the domain of every connection. The configuration stays in Emacs, as everything else
does, and Emacs stays outside the sandbox: what holds the rules must not be confined by them,
and on macOS a sandboxed process cannot start another under rules of its own. So
~lispm-sandbox-level~ (None, Low, Middle, High, or Custom: the user's own rules, a plist of the
same few kinds srt has) becomes srt's settings each time ~run_shell~
starts a command or an MCP server starts, and a change reaches processes already running through
srt's control channel, a named pipe Emacs keeps open to each: their network rules change at once;
their file rules were fixed when they started, and the change says which to restart. When srt
cannot be had, or the root is on another machine, which srt cannot confine, the command fails
with the reason: a sandbox that stepped aside when missing would be worse than none, since it
would still be trusted. Emacs Lisp stays unconfined, so ~exec~ keeps asking; and no level lets
a command write Emacs's configuration or ~lispm-directory~, which holds srt itself.

*A root on another machine.* Hosted harnesses give each agent a computer of its own, a VM in
their cloud, so that what it does cannot reach the user's. LispM's agents live in the user's
Emacs, which is the point of them; what can go elsewhere is their hands. Emacs reaches other
machines through TRAMP, so an agent's root may be a TRAMP directory: ~/ssh:vm:/work/~, or
~/docker:box:/work/~ for a container on this machine. Its tools then work there by TRAMP's file
name handlers, as they work here: ~read_file~ and the edit tools; ~list_directory~, in one round
trip; ~search_files~, which reads remote files through TRAMP still (without decompressing or
decrypting them, as here); and ~run_shell~, which TRAMP's ~make-process~ runs in the root on that
machine, with that machine's shell (~shell-file-name~ as TRAMP's connection-local variables
give it). An absolute path that names no machine, ~/etc/hosts~ or ~~/notes~, names a file there
(~lispm--expand-file-name~), since to a command there that is the file meant; the system prompt
says so, and the rule that writes outside the root ask goes by the same file. After a call that
may have changed files, TRAMP forgets what it knew of that machine's files, as it does after
~process-file~ but not after ~make-process~ (~lispm-tools--flush-remote~), and the buffers of
those under the root are checked through its connection and reverted.

What stays here is the image: ~eval_elisp~ and the other ~exec~ tools run in the user's Emacs
wherever the root is. So ~((shell . auto))~ lets an agent run commands in its machine unasked
while its Lisp still asks; and approving one of its commands for good allows ~run_shell~ for
good, since a command there cannot reach the policy (~lispm-tools-elsewhere-p~: a remote root
whose host is not one of the names TRAMP knows for this machine, as those of ~/sudo::/~ and
~/su::/~ are). That holds only while the other machine cannot write this one's files: a container
that mounts the user's home directory reaches their Emacs configuration, and with it everything.
Such a root has the in-memory journal only (section 12).

*Approval is an org TODO state.* A call that needs approval is recorded as
~** WAITING edit_file ...~, with a diff preview and the ~why~ below it. The tool's ~:diff~
gives the text before and after; ~diff~ runs in the background (~lispm-exec~), and the call
is announced, its preview written, ~lispm-approval-functions~ run and the message saying
where to answer given, once the diff is made, if the call still awaits approval. To decide:

- in the chat, a box shows the command or diff and the ~why~ and asks as Claude Code does:
  ~1~ yes, ~2~ yes and don't ask again for this tool (for an ~exec~ call, or a shell command
  on this machine, this exact call),
  ~3~ no and say what to do instead (the answer is passed on to the model); a call a Lisp
  program makes is asked about the same way, the box saying so;
- in the org transcript, ~C-c C-y~ (~lispm-review~): y to approve, n to deny (optionally with
  a reason), a to allow that tool for the rest of the Emacs session;
- or change the TODO state directly with ~C-c C-t a~ or ~C-c C-t n~;
- or work through ~M-x lispm-agenda~, an org agenda view of WAITING calls across all agents.

Approval *never blocks*: the agent sits in ~waiting~ while the user and the other agents carry
on; the mode line shows ~λ[coder!]~ when something awaits approval.

*Approval in place* (lispm-edits.el). A diff in the chat shows a change out of its context; the
buffer it would change is the context. So a call that would change a buffer is also laid over
that buffer, the lines it removes struck out and the new ones after them, under a tag naming
the agent, while it awaits approval; once made, the change is typed in behind the agent's
cursor and glows a moment. Even earlier, while the model is still writing the call, its text
streams into the same place: the API adapters report each piece of a call's input
(~lispm-tool-input-functions~), and the partial JSON is read as far as it goes. Tools take part
by saying what a call would make of which buffer (~:changes~ in ~lispm-deftool~); the effect
of a call that ran is learned from ~lispm-buffer-change-functions~, which every write runs, so
reverts are shown too. None of it touches the text: overlays only, and the buffer comes into
view in a window of LispM's choosing, never over a chat, where the approval is given.

*Approval survives restarts.* A call's heading holds all it needs (id, tool, input, state), so a
session saved while calls await approval and opened again after Emacs restarted takes them up
(~lispm--resume-calls~): WAITING calls await approval again, and once they are settled the turn
goes on. Calls that were running are recorded as interrupted, their processes gone, unless
something can still finish them (~lispm-resume-call-functions~: an ~ask_agent~ call whose
helper can still reply, section 7). The in-memory table of pending calls is only a cache of
what the transcript says.

*The world persists.* A Lisp Machine's world is saved and comes back as it was; so does an
agent's, for what Emacs holds of it in memory alone:

- *Turns.* A session is saved as a turn starts, before each request and whenever calls are
  recorded; a response streaming in is shown in the session but never saved (~lispm--unsaved~),
  so the file holds what the next request is made from. A turn Emacs stopped in the middle of,
  with nothing left to await, its calls interrupted or its request lost, waits at an
  ~interrupted~ condition when its session opens again: ~continue~ asks the model again,
  ~abort~ ends it as it would have ended.
- *Inboxes.* What waits for an agent, and the input its turn under way handles, is kept in the
  project's ~inbox.org~ as well as in memory (lispm-inbox.el): one heading per input, QUEUED,
  then RUNNING while its turn is under way, removed once it is over and whoever waited has the
  reply. A session opened again takes its queued inputs back and handles them next; a RUNNING
  one says which turn was interrupted, and who waits for its reply. A standing agent, declared
  again as Emacs starts, takes up at once what its inbox holds (~lispm-agent-declared-functions~);
  ~lispm-resume-agents~ resumes every session an inbox holds inputs for.
- *Delegations and ceilings* survive as section 7 says.
- *The journal.* For a project in git, snapshots of the work tree as a turn begins and ends are
  commits in a repository of LispM's own (~projects/<project>/journal.git~, the project's work
  tree its work tree, so the project's own repository gets nothing), made asynchronously from
  the files git lists, a turn's first request waiting for the first. ~lispm-revert-turn~ and
  ~lispm-turn-diff~ take a turn's files from them, buffers and unsaved edits from memory: so
  rollback covers what ~run_shell~ and ~eval_elisp~ changed, and turns from before Emacs
  restarted.

What is left to forget is right to forget: the calls allowed "for good" (~allowed~) last as
long as the Emacs session they were allowed in.

*Restarts: a stopped turn waits.* On a Lisp Machine an error does not end the computation: the
debugger shows it and offers proceed options. In LispM a turn that stops early, because a request
failed after its retries or could not be made (no backend, say), because it reached
~lispm-max-steps~, or because a response was cut short, refused or paused, does not end
either: it waits at a *condition*, as a call waits for approval,
until a *restart* is chosen (~lispm-signal~, ~lispm-condition-types~). The condition is a
top-level heading, ~* WAITING Condition: Request failed~, whose properties name its type, its
id and its restarts and whose body is the message. No role claims it, so the model never sees
it. Its restarts:

| Condition           | Signaled when                                        | Restarts, default first                                   |
|---------------------+------------------------------------------------------+-----------------------------------------------------------|
| ~request-failed~    | a request fails after its retries, or cannot be made | ~retry~; ~use-model~: another backend or model; ~abort~   |
| ~step-limit~        | a turn reaches ~lispm-max-steps~ requests            | ~continue~ for as many again; ~abort~                     |
| ~output-limit~      | a response hits the output limit                     | ~retry-larger~: drop it, twice the limit; ~keep~; ~abort~ |
| ~context-full~      | a response fills the context window                  | ~compact~, then go on; ~abort~                            |
| ~refused~           | the model refuses                                    | ~retry~: drop it, ask again; ~abort~                      |
| ~paused~            | the model pauses (~pause_turn~)                      | ~continue~; ~abort~                                       |
| ~compaction-failed~ | a handover fails                                     | ~retry~; ~skip~: carry on in the long session; ~abort~    |
| ~tool-error~        | a tool fails (~lispm-debug-tool-errors~)             | ~report~ it to the model; ~retry~; ~use-value~; ~abort~   |
| ~interrupted~       | a session opens where Emacs stopped mid-turn         | ~continue~: ask the model again; ~abort~                  |

They are chosen wherever approvals are given: the chat shows a box with the restarts numbered;
in the org transcript ~C-c C-y~ offers them, and changing the heading's TODO state to ~DONE~
takes the default, to ~DENIED~ aborts; the agenda lists waiting conditions with waiting calls.
Whatever the user asks of the agent next goes past the condition, stopping there: a message
written in the chat, one written in org under a new ~* User~ heading after the condition,
~/clear~, ~/compact~. In Lisp, ~lispm-restart~ chooses one, and handlers choose without asking,
as ~handler-bind~ would, at once or after a delay, at most so many times in a turn (for a call's
condition, in that call), then perhaps another restart:
~((request-failed retry :after 60 :times 2 :then abort))~. Turns the user
started go by ~lispm-condition-handlers~: they wait for the user, except that a paused response
goes on. Turns started
by another agent's message (a helper's) or by an event (a hook, a timer) go by
~lispm-unattended-condition-handlers~, since nobody may be watching and someone, or the next
event, waits for them: by default a failed request is tried again twice, a minute apart, then
the turn stops, as one reaching the step limit or refused does at once; a response cut short is
asked for again with twice the limit, or the session handed over, once; a paused one goes on; a
failed handover is skipped; a turn Emacs stopped in the middle of goes on, once its session
opens again. Dropping a response (~retry-larger~, ~refused~'s ~retry~,
~compact~) tags its ~* Assistant~ section ~:ignore:~: it stays on record, no longer sent, and the
chat says it was left out. A raised limit holds for the rest of the turn, unless the server
refuses it: then it is lowered again, and the failed request says so. ~keep~ tells the model to
go on in a ~* From LispM~ section, LispM passing on the user's choice, which the system prompt
says to follow as theirs; ~continue~ sends a paused response back as it is, which is how the
API resumes it. ~compact~ hands the session over in the middle of the turn, which goes on from
the summary, the agent first told to save what should outlive the session, as a handover between
turns asks first; a condition that stops a turn in its middle says so (~:RESUME: t~), so that
~skip~ goes on with it. Between turns, stopping at a failed handover drops the input that asked
for it, telling whoever sent it, and records an event: there is no turn to end.

*Tool errors* go to the model, which made the call and can usually handle them: a file not
found, an ~old_text~ that no longer matches. ~lispm-debug-tool-errors~ (nil, t, or a list of
tool names) makes them stop instead, as ~debug-on-error~ enters the debugger: the failed call
waits at a ~tool-error~ condition of its own, carried by the call rather than the turn. Its
heading goes back to ~WAITING~, with ~:CONDITION: tool-error~ and a ~*** Stopped~ subsection
holding the error, so the agenda lists it and a reopened session takes it up, as calls awaiting
approval; the chat asks about it where it would ask for approval, but it is not one: approving a
tool for the session leaves it alone, and aborting the turn names ~abort~ on it. ~report~ gives
the model the error as the result, as without the option; ~retry~ runs the call again, once the
user has fixed what it needed (a handler's ~retry~ runs it only if the policy would run it
unasked, else it awaits approval again); ~use-value~ gives the model a result the user types;
~abort~ ends the turn, the call failed, the others stopped, inputs waiting kept. A chosen
restart is named on the Stopped subsection (~*** Stopped: retry~). Unattended turns report each
failed call at once; a call interrupted with C-g never stops.

A chosen restart is recorded on the heading (~DONE~, ~:RESTART: retry~, and the value it was
given, ~:VALUE: (other . "model")~, which a reopened session uses again); ~abort~ removes it and
ends the turn with the note a turn stopped early always ended with, so the transcript is as it
was before restarts existed. A condition survives a restart of Emacs like a call awaiting
approval: reopening the session waits at it again, and since requests are built from the
transcript, ~retry~ needs nothing else saved. Meanwhile the agent is busy: messages and events
queue in its inbox, a helper's caller keeps waiting, and ~lispm-abort~ stops the turn there. A
helper the user writes to does not retire once it has replied to its caller: it stays to answer
them.

*Explainability* comes in four layers: the ~why~ of every write, shell or exec call; the transcript
itself (every call's input, state and result); ~lispm-show-request~ (the raw request the model
sees); the git history and per-turn diffs (~lispm-turn-diff~).

*Trust boundary*: messages from other agents (~[Message from agent X]~) and hook events
(~[Event: ...]~) are defined in the system prompt as requests from colleagues, not as
instructions from the user. Writes and commands they lead to go through the same approval
policy.

* 6. Continuous operation: hooks and the event loop

Agents do not only answer when asked. Any Emacs hook or timer can wake one up:

#+begin_src emacs-lisp
;; Have coder look at failed compilations.
(lispm-watch 'coder 'compilation-finish-functions
  :when (lambda (_buf status) (string-match-p "abnormally" status))
  :prompt "The compilation failed. Read the *compilation* buffer, find the cause and fix it.")

;; Review the task list every hour.
(lispm-every 'planner 3600 "Look at your open tasks and move one of them forward.")
#+end_src

- A trigger produces an ~* Event: ...~ input in the agent's inbox, which outlives Emacs (section
  5); idle agents process their
  inbox in order. Events of the same name are coalesced in the inbox, and bursts of hook runs
  are debounced.
- *Hook runs an agent caused itself do not wake it* (~lispm-current-agent~ is bound while its
  tools run), and the runtime saving its own files is not an event either. This prevents
  save → trigger → edit → save loops.

* 7. Multi-agent collaboration

Agents share one Emacs: the same buffers, the same files, the same event loop. Collaboration
needs only three tools, and three more to see each other, to answer with data and to start
agents that work on their own:

- ~list_agents~: who is running, in which project, doing what, and which roles exist
  (~inspect_agent~ shows one in depth); both are deferred, since the system prompt already
  names the running agents and the roles;
- ~send_message~: delivered to the other agent's inbox, where it becomes a
  ~* Message from X~ turn;
- ~ask_agent~: *delegation*. The caller's tool call stays pending (an asynchronous tool); when
  the other agent's turn ends, its final reply becomes the result. The caller occupies no
  thread and blocks no one meanwhile. Named a role instead of an agent, ~ask_agent~ starts a
  helper of that role in the caller's project and retires it once it has replied: a subagent,
  whose session stays on record. *A helper may do no more than its caller*: for each permission
  class its policy is the stricter of its role's and its caller's (its ~ceiling~), so a reviewer
  that may not write cannot get writes done by starting a coder.
- ~start_agent~: an agent of a role, started in the caller's project or another, that *works on
  its own*: nobody waits for its reply, and it stays once it has replied, for the user and the
  other agents to talk to. It gets its caller's ceiling as a helper does. Started outside the
  caller's project, it could do there what the caller may do in its own, where the caller's
  writes always ask; so that call asks too, whatever the policy says (a function of
  ~lispm-tool-action-functions~). Deferred, as seldom needed.

What passes between agents need not be only text. A reply can carry a *value*: the agent asked
returns one with ~return_value~ (any JSON: a list of places, an org subtree as text), the turn's
callbacks get it as the reply's ~lispm-value~ property (~lispm-reply-value~), and ~ask_agent~
gives it to the model after the reply, as JSON. And messages carry *references* the receiver's
tools resolve: places as org links, ~[[file:PATH::LINE]]~, which every tool taking a ~path~
accepts (~read_file~ reads from the line), and buffers as ~[[buffer:NAME]]~, which tools taking
a ~buffer~ accept (~lispm-tools-reference~); the system prompt says so, and the chat presents
them. A write a link names outside the agent's root asks as any does.

Concurrency:

- *No locks are needed*: the event loop is single-threaded and each tool call is atomic.
  Edits replace exact old text with new text; if someone else (or the user) changed that text
  first, the replacement fails and asks the model to re-read: *optimistic concurrency*.
- *Deadlock detection*: ~ask_agent~ follows the ~waiting-on~ edges and refuses a request that
  would close a cycle. An agent that asks several in one response waits on all of them, so
  the edges form a graph, not a chain.
- Every agent's system prompt lists the running agents and the roles, so the model knows
  whom to delegate to.
- *Isolation, when wanted*: optimistic concurrency keeps agents from clobbering each other,
  not from seeing each other's half-done work. A helper can work apart instead, in a git
  worktree of its own (the ~worktree~ skill, section 11). Delegation itself is
  ~lispm-delegate~, which ~ask_agent~ and the skill's ~worktree_ask~ share: same ceiling,
  same deadlock check, same retirement.
- *Delegation outlives Emacs.* The caller's ~ask_agent~ call records on its heading whom it
  asked (~:ASKED:~, the other session's id), and the request, in the other agent's inbox, whom to
  reply to: the caller's session and call. Should Emacs stop before the reply, opening the
  caller's session opens the other's again; the request is taken up there (queued, or its turn
  interrupted and, unattended, gone on with), and the reply, when it comes, settles the call. A
  helper's ceiling is recorded in its session (~#+lispm_ceiling:~), so a helper's session opened
  again, by a restart or by hand, may still do no more than its caller.
- *Characters are reached by name* (section 1), as =@Ada=: ~ask_agent~ and ~send_message~ go to its
  conversation in the asker's project, started there if it has none, and the editor's agents do
  the same, told so by their server; an app's is its own. Every system prompt names the
  characters and says that the user's =@Name= is to be passed on, and the chat completes =@names=.

* 8. Handing over: long conversations

A conversation cannot grow forever, least of all a standing agent's. A session's size is the
one the model's latest response reported (every input token, cached or not), plus a token for
every three bytes written since; bytes, not characters, since a token is about four characters
of English but about one of Chinese, three bytes. When the size passes ~lispm-compact-threshold~
(default 120k tokens), the session first makes room the cheap way: the output of all tool calls
but the latest ~lispm-compact-keep-results~ (default 10) is cleared. It stays in the file, its
~*** Result~ heading tagged ~:cleared:~ (remove the tag to send it again); requests carry a line
saying it was cleared, and the model can make the call again. Clearing changes an early part of
the conversation, so the prompt cache is built again: it is done only if it frees
~lispm-compact-clear-at-least~ tokens (default 10k). It can happen before any request, in the
middle of a turn too.

If that does not bring the session under the threshold, the next turn first hands it over:

1. the agent gets one turn to save what should outlive the conversation: durable knowledge with
   ~remember~, unfinished work with ~task_add~ (~lispm-compact-save-memory~);
2. it writes a handoff summary (goals, decisions, state of the work, next steps), in a request
   without tools, told which of the latest turns follow it, so that it says little about them;
3. the conversation continues in a new file of the same session (same agent, same id), whose
   first section, ~* Summary~, holds the summary and whose header links back to the old file;
   the latest ~lispm-compact-keep-turns~ turns (default 2) follow it as they were, fewer if
   they would take more than a quarter of the threshold, never the turn that saved memory, and
   never all of them; the old file ends with a link forward, and the system prompt is rebuilt,
   so memory saved in step 1 is in it; the session keeps its title in session lists;
4. the input that triggered the handover starts the first turn there.

*At idle.* So that the request after a long turn does not wait for all this, a session past
~lispm-compact-idle~ of the threshold (default 0.75) when a turn ends is compacted once Emacs is
idle: older tool output is cleared, and if that is not enough, the agent saves memory in a turn
of its own (step 1) and the summary (step 2) is written in the background while the agent stays
free. Input given it meanwhile starts at once in the session as it is, and the summary, out of
date, is thrown away; so is one that comes once the session changed. Otherwise the session is
handed over as in step 3, with no input to start. A session the user is writing in is left
alone. Since each attempt costs a turn and a request carrying the whole session, it is made
once per session: given up, it is left to the start of a turn past the threshold, as above,
which then neither saves memory again nor asks for a second summary while one is on its way.

~M-x lispm-compact~ hands over on demand, like Claude Code's ~/compact~. This is the "simple
compaction" model vendors recommend, with the latest turns kept so that the work under way
goes on from what was actually said: nothing older is replayed but the summary, so little stale
reasoning is sent and the prompt cache restarts once, at the handover. Handovers happen only
between turns, and only for sessions that hold a response.

* 9. Model backends: two API shapes

LispM speaks both shapes model servers offer: OpenAI Chat Completions, the most widely
implemented (OpenAI, Ollama, vLLM, LM Studio, llama.cpp, OpenRouter, ...), and Anthropic
Messages. Internally there is a single conversation format, the Messages shape transcripts
parse into. Each API shape is an adapter that translates requests out and responses back,
registered in ~lispm-api-shapes~ with its path, request builder, headers and stream decoder.
Supporting another shape, such as OpenAI's Responses API, means adding one entry.

Translation to and from Chat Completions ([[file:lisp/lispm-openai.el][lispm-openai.el]]):

| Messages shape                              | Chat Completions                                             |
|---------------------------------------------+--------------------------------------------------------------|
| system prompt                               | a leading ~system~ message                                   |
| text blocks                                 | message ~content~                                            |
| ~tool_use~ blocks                           | the assistant message's ~tool_calls~ (arguments as JSON text) |
| ~tool_result~ blocks                        | one ~tool~ message per result; failures prefixed ~Error:~    |
| thinking and other Messages-only blocks     | not sent                                                     |
| a ~reasoning~ block, shown, never sent back | ~reasoning_content~ or ~reasoning~ in responses              |
| stop reason ~tool_use~, ~max_tokens~, ~refusal~ | finish reason ~tool_calls~, ~length~, ~content_filter~   |

Streamed tool calls arrive as fragments keyed by index; the decoder assembles them, so parallel
calls work whatever order their fragments interleave in.

A backend (~lispm-backends~) names an endpoint, its shape and the features to use:

| Feature                 | Shape     | Meaning                                                     |
|-------------------------+-----------+-------------------------------------------------------------|
| ~streaming~             | both      | server-sent events, shown live in the buffer                |
| ~reasoning-effort~      | openai    | send the agent's effort as ~reasoning_effort~               |
| ~max-completion-tokens~ | openai    | call the output limit ~max_completion_tokens~ (OpenAI's API) |
| ~stream-usage~          | openai    | ask for token usage while streaming                         |
| ~adaptive-thinking~     | anthropic | progress-update thinking blocks, thinking prefix binding    |
| ~fallbacks~             | anthropic | server-side refusal fallbacks                               |
| ~eager-input~           | anthropic | tool input streamed without buffering                       |
| ~tool-errors~           | anthropic | the ~is_error~ flag of tool results                         |

| Preset      | Shape     | Features                                                         |
|-------------+-----------+------------------------------------------------------------------|
| ~openai~    | openai    | streaming, reasoning-effort, max-completion-tokens, stream-usage |
| ~anthropic~ | anthropic | all of the above for its shape                                   |

*No provider is assumed.* The presets are the two first-party APIs; any other server, local or
hosted, is an entry of the user's, and it is the shape that matters, not the provider. Nor is
there a default backend: ~lispm-backend~ names one, or, left nil, the first entry whose API key
is set in the environment serves (~OPENAI_API_KEY~, ~ANTHROPIC_API_KEY~, or an entry's
~:key-env~). With none, a message gets an answer at once saying what to set, rather than a
connection error from a guess. The ~anthropic~ preset's default model is ~claude-opus-5-5~, with
every Messages feature enabled, including server-side refusal fallbacks (~fallbacks:
"default"~).

Servers that translate between the two shapes can get the details wrong: stop reasons above
all. So the runtime executes the tool calls of any response that was not cut short
(~max_tokens~, ~refusal~), whatever its stop reason; a feature a server lacks, such as
~tool-errors~, is left out of its entry, and LispM falls back (failures marked in the text).

* 10. MCP servers and images

Tools need not be written in Lisp: the tools of any Model Context Protocol server become an
agent's tools. LispM does not speak the protocol itself; it depends on mcp.el, which does, and
adds what an agent runtime needs on top:

- *Registration.* When a server lists its tools, each becomes a LispM tool named
  ~mcp__SERVER__TOOL~ whose schema is the server's own (~lispm-tool~ has an ~input-schema~
  slot for tools that are not defined by ~lispm-deftool~ parameters). JSON crosses between the
  two libraries' conventions (alists and ~:false~ here, plists and ~:json-false~ in mcp.el).
- *Permissions.* MCP tools have the permission class ~mcp~, which asks by default, like
  ~write~, ~shell~ and ~exec~: a server can do anything. A server's ~:permission~ gives its tools
  another class; "don't ask again" in the chat allows one tool at a time. Before a server's
  tools are registered, the functions of ~lispm-mcp-register-functions~ see them as the server
  lists them, and may keep some back, so that no agent reads what they say, or have every call
  of them ask: a server may change what its tools say from one start to the next.
  ~lispm-mcp-refresh~ registers a running server's tools again, and ~lispm-mcp-tool-origin~
  tells which server a tool came from.
- *Deferred tools.* A server's tools are deferred (see below): the server starts when an
  agent first searches them. A server with ~:defer nil~ starts when a session opens instead
  (~lispm-mcp-autostart~), and since its tools should be there from the session's first
  request on, for the model and for the prompt cache, a request waits while it is still
  starting (~lispm-request-wait-functions~, ~lispm-mcp-start-timeout~); the chat says so.

*Two steps to a tool.* Tools cost room in every request: Peekaboo's 26 take about 14,000
tokens, and a few servers would crowd out the conversation. So an agent carries a core layer,
the tools it commonly needs, and the others are deferred: offered only once the model has
found them with ~search_tools~, which lists the sources of deferred tools (an MCP server, with
its ~:description~) and searches their tools by keywords, or takes exact names
(~select:A,B~). The search is fuzzy (~lispm-tools-search-score~): a word matches one it equals,
begins, is begun by or holds, or, if five letters long or more, one it misspells by a letter or
two after the same first letter (one letter off a shorter word is another word: "chat" and
"what"); names are taken apart at ~_~ and ~-~, a name counts above a description, and what
matches every word comes before what matches one well. What scores under a third of the best
is left out (~lispm-tools--search-cutoff~): it matched by chance, and a tool found is offered
in every request after. It finds skills too, and whatever else ~lispm-tool-search-functions~ offers
(section 11). The tools it finds are loaded for the agent and offered from
its next request on, for the rest of the session (~lispm-agent-loaded-tools~); the tool list
changes then, which costs the cached request prefix once. A resumed session loads them again
from its transcript, which records the searches and the calls. Sources register through
~lispm-tool-sources~, so deferred tools need not be MCP tools: ~lispm-deftool~ takes
~:deferred t~, and LispM's own tools for Lisp in the image (section 3) are such a source.

*Tools an agent defines.* On a Lisp Machine a command written in the running world was part of
the system at once. An agent defines a tool the same way, with ~lispm-deftool~ in the code
~eval_elisp~ runs or in a skill's code, and the tool is deferred whatever its definition says,
and loaded for that agent at once (~lispm-tools--adopt~): the agent has it from its next step
on, as if it had found it with ~search_tools~, and the result of the call says so. Left as its
definition made it, in the core layer, it would reach no running session, the agent's own
included, and every agent's next one. Other agents find it with ~search_tools~. Only tools new
to the registry are deferred so: one defined again keeps its place, so that an agent reloading
LispM's own code leaves the core layer as it was. Tools the user defines are not touched.

*Images.* A tool result can hold images: Peekaboo's ~see~ returns a screenshot with its map of
the screen. The transcript cannot hold image data, and should not: base64 would swamp it. So
an image is a file next to the session (~SESSION-ID.images/0001.png~, kept out of git) and
the result's section links it, one ~[[file:...]]~ per line, which org can show inline. The
parser turns each link into an image block, read from the file when the request is made.
Only the latest ~lispm-context-images~ images are sent; older ones become a line of text, a
batch at a time, so that the request prefix, and the cache bound to it, changes only once a
batch. Chat Completions accepts images in user messages but not in tool messages, so there the
images follow the tool messages in a user message of their own.

Computer use is then not something LispM implements: on macOS, Peekaboo is configured as a
server, and an agent sees the screen through ~see~ and acts through ~click~, ~type~, ~press~,
~scroll~ and the rest, on accessibility elements rather than guessed coordinates.

* 11. Skills: knowing how

A skill is what it takes to do a kind of thing with Emacs, written down: which functions, in
which steps, with which pitfalls. It is an org file, ~NAME.org~ or ~NAME/SKILL.org~, with a
~#+title~ and a ~#+description~, instructions for the model, and source blocks marked
~:lispm load~ whose code defines helper functions, and tools if the skill wants them (they
become deferred tools of the agent that loads it). Skills come from ~lispm-skill-directories~:
LispM's own ~skills/~, the user's ~~/.lispm/skills/~, then the agent's project's
~.lispm/skills/~, a later skill replacing an earlier one of the same name. For an agent working
in the home directory, ~~/.lispm/skills/~ is the user's, not a project's.

*Skills are the system's manuals.* Every part and app of the system brings the skill that
says how to use it, with the tools to do so. Programs other than LispM register theirs through
~lispm-skill-sources~: functions returning the directories of their skills, each with its
~:origin~, a name shown with them. They come before ~lispm-skill-directories~, so the user's
own skill replaces one of theirs of the same name, and their code is evaluated unasked, as the
program bringing them is. LispM Desktop registers so the skills of the system it ships and
those its App Store installs with the apps they drive; LispM knows nothing of either.
~lispm-skills-directories~ tells every directory, for tools such as LispM Security's
inventory.

Skills are found and loaded in two steps too. No list of them is sent: there may be many, and
a list would change the request prefix whenever one is installed. ~search_tools~ finds them,
by their name, title, description and headings and by the tools their code defines, read
from the code without evaluating it (~lispm-skills--index~, kept until the file changes): a
~lispm-deftool~ form, or a ~lispm-register-tool~ one naming its tool literally, at top level
or in ~progn~, ~with-eval-after-load~, ~when~ or ~unless~. It names each skill with its
origin and its tools, and loads none of those tools: a skill's tools come with the skill, so
the model reads how to use them first. The role's tools are kept to: a skill is shown only
to an agent whose role gives it ~skill~, which gives ~search_tools~ with it. When a request
calls for a skill, the model loads it with ~skill~, by name (a name missed gets the nearest),
its text becomes the call's result, so the conversation holds it from then on without
changing the request's tool list, and its code is evaluated. A resumed session evaluates
again the code of the skills it loaded.

*A project's skills* may come from anywhere, as a cloned repository does, so their code runs
only once the user has seen it and agreed. Loading one asks, through the call of ~skill~, as a
Lisp program asks for the calls it makes (~lispm-call-ask~): the chat shows the code, the
transcript records the question under the call (~*** Asks: trust_skill~) with the code as its
preview. ~1~ runs it this once; ~2~ trusts it for good, pinned by a hash: the sha256 of the
~:lispm load~ blocks and, for a skill that is a directory, of the other files in it, which the
code may load. The pins are a Customize variable, ~lispm-trusted-skills~, saved as the user's
other settings are; ~M-x lispm-trust-skill~ shows a project's skill's code and pins it, or with
a prefix argument unpins it. While the hash matches, the code runs unasked, in a resumed session
too; once the code changes, it is asked about again. What runs is what the user saw: the hash
is computed again when they answer, and code changed meanwhile does not run. Refused, the skill
is loaded without its code, and the model is told so.

*Agents write skills.* What an agent defines in the running Emacs lasts until Emacs exits, and
what it found out about doing a thing, until its conversation ends. ~write_skill~ keeps both,
the way a Lisp Machine user saved a new command into the system: the agent proposes a name, a
description, instructions and code, and the user reviews the org file they make, as a diff
against the skill of that name it would replace. It is of class ~exec~, since its code is
evaluated in every later session that loads the skill, and it always asks (section 5), so that
only the user decides what joins their skills. Approved, the code is evaluated first, and
the file is saved in ~lispm-write-skill-directory~ (the user's ~~/.lispm/skills/~) only if that
succeeds: a skill whose code fails, or does not read, is not saved, and the model is told why.
Its tools are the agent's at once, deferred; the result says the skill was loaded, so a resumed
session loads it again, and from then on it is listed for every agent. A name is lowercase
letters, digits, ~-~ and ~_~; one that LispM's own skills or the project's have is refused,
since a skill saved under it would not replace theirs.

*Installing skills.* ~lispm-install-skill~ copies a skill from elsewhere, a file or a directory,
into the same directory, under the same rules for names. A skill there is the user's, its code
evaluated unasked, so installing one is trusting it: the user sees its code first, or the diff
against the skill it replaces, the files beside it included, and what is installed is what they
saw, a skill whose code changed meanwhile not at all. ~lispm-delete-skill~ deletes only skills
of that directory.

The first skill is ~web~: searching the web and reading pages. Pages are rendered by Emacs's
own WebKit (xwidgets) out of sight, scripts and all, with the cookies of the user's own
xwidget browsing; without xwidgets, url.el fetches the HTML. Either way the HTML is parsed
by libxml, its main content found by eww's readability scoring and rendered as text by shr,
the same code eww uses to show pages. A widget's events, the results of its scripts among
them, wait until something wakes Emacs's event loop, so a timer watches the load and keeps
the loop turning. Its tools have the permission class ~web~, which asks by default: a fetch
can carry data out.

The second is ~worktree~: delegating to a helper that works in a git worktree of its own, on a
branch of its own (~worktree_ask~, ~worktree_list~, ~worktree_remove~). It is a skill rather
than part of the core because it depends on git's toolchain, as ~web~ depends on a browser:
an agent that needs it loads it, and the rest of LispM does not assume a repository. What the
core keeps is what is not about git commands: delegation with a root of the caller's choosing
(~lispm-delegate~), and the rule that a linked worktree is its main worktree's project
(section 2).
The worktrees are made with git itself, asynchronously: Emacs 31's ~vc-add-working-tree~
prompts for the branch, and Emacs 30 has no such function. A helper is told to commit its
work on its branch; when it replies, the result lists its commits, what it left uncommitted
and the changes against the base, or, if it changed nothing, its worktree and branch are
removed at once.

* 12. Known limitations and next steps

- *Drafts are context in the org interface*: with ~lispm-interface~ set to ~org~, if another
  agent's message arrives while the user is typing under ~* User~, the draft is sent along as
  a user message. The chat keeps drafts out of the transcript.
- *Searching is slower than ripgrep*: on a repository of 8,000 files a search takes about
  1.3 s against ripgrep's 0.2 s, without freezing Emacs, except for listing the project's
  files (~git ls-files~ through project.el, about 0.3 s there).
- *The chat redraws by re-reading the transcript*: a redraw parses the org buffer again
  (only when it changed) and redraws from the first item that differs. That is cheap for
  ordinary sessions; very long ones would want incremental parsing.
- *Session-level backend switches lose reasoning*: thinking blocks only go back to the
  Messages shape, and reasoning text from Chat Completions servers is never sent back, so a
  session that changes backend mid-way continues without the earlier reasoning.
- *A program's check is an allowlist, not a proof*: ~run_lisp~ trusts Emacs's declarations
  of what is free of side effects, and generic functions (~seq-*~) dispatch on their
  arguments, so an object already in the image may run methods of its own. A program can
  still hold Emacs up, say with a huge ~make-list~; C-g stops loops. What the allowlist does
  not know, it refuses.
- *A turn's snapshots show every change made meanwhile*: the journal in git compares the work
  tree as a turn began with the tree as it ended, so changes the user or other agents made to
  files of the project during the turn are counted as the turn's, and reverted with it (the
  in-memory journal knows only the buffers the agent's tools changed). Projects outside git have
  the in-memory journal only, which does not outlive Emacs.
- *A remote root has no snapshots*: the journal repository is on this machine, git needs the
  work tree it records on its own, and a snapshot reads the project's files one by one, a round
  trip each through TRAMP. So an agent whose root is on another machine has the in-memory
  journal only, of its tools' edits; a VM or a container can be snapshotted by its own means.
  Direction: a journal repository on that machine, driven through ~process-file~.
- *A remote root is slower*: ~search_files~ reads each file through TRAMP; a command runs in
  a shell TRAMP keeps for the connection, with a terminal, unless TRAMP's direct asynchronous
  processes are on for that machine (~tramp-direct-async-process~). TRAMP sets ~PAGER=cat~
  there, so git and the like do not wait at a pager.
- *Handovers inside a turn wait for a response to fill the context*: a turn that outgrows
  ~lispm-compact-threshold~ clears old tool output before its requests, but a turn that
  outgrows the model's context hands over once a response stops with the window full
  (~context-full~), not before; a request whose input alone is too large fails instead
  (~request-failed~). Direction: server-side compaction with the first-party API.
- *A definition is found by its text*: ~edit_definition~ and ~eval_definition~ find a form
  by the searches find-function makes, but not by its last resort of expanding macros, so a
  definition a macro makes without a form naming it (a ~cl-defstruct~ accessor) is not found,
  and ~edit_file~ is the way to change it; of several definitions of a symbol in a file, the
  first is meant, as with find-function. The file an ~edit_definition~ call writes is found
  when the call is decided and again when it runs: Lisp evaluated in between that moves the
  definition to another file takes the edit with it, unasked. Only ~exec~ calls evaluate
  Lisp, and they are outside the permission model (section 5).
- *Emacs waits for xref*: xref's backends answer synchronously, and the references of Emacs
  Lisp are found by xref's default means, find and grep over the project's files (with
  ~everywhere~, over all of ~load-path~ as well), as M-? finds them; Emacs is held meanwhile.
- *Trust covers what a skill ships*: a project's skill is pinned with its code and the files
  beside it, not with what that code reaches beyond them, such as a package it requires.
- *A redefined tool keeps its old schema in running sessions*: its new body runs at once, but a
  new parameter reaches the model in the next session, or the next handover.
- *More Emacs-native tools*: magit operations, org-babel execution, window layout: each is
  just a ~lispm-deftool~ away.
- *A shared blackboard*: an org file every agent can read and write, as a collaboration
  medium more durable than messages.
